# LLM 教练 A/B 实测结果

模型：`qwen2.5-7b-instruct-q4_k_m`，llama-server `-c 16384 --parallel 2`。
对局：3 张图 × seed 1–10 = **30 局配对**，`ticks=150000`（约 13 回合/局）。
规则组与 LLM 组使用完全相同的 map/seed/ticks，仅教练来源不同。

> 2026-11-06 更新：补做了"单局串行校准"和"新配置（顾问模式 + 时效闸 + 低延迟）"两组实验，
> 修正了此前"并行跑局导致延迟虚高"的结论偏差。

## 三组实验

| 组 | 配置 | 目录 |
| --- | --- | --- |
| 规则 | 纯规则教练 | `build-evidence/final-rule` |
| A. 旧配置（串行校准） | 7B / 全事件 / 260 tokens / 手册 8KB / 单局串行 | `build-evidence/step1-calib` |
| B. 新配置 | 7B / 回合开始+下包 / 120 tokens / 手册 4KB / 顾问模式 / 时效闸 / 单局串行 | `build-evidence/step5-final` |
| （历史）并行跑 | 旧配置 + 2 局并行（延迟被拥塞放大） | `build-evidence/final-llm` |

## 结果（30 局配对）

| 指标 | 规则 | A 旧配置 | B 新配置 |
| --- | --- | --- | --- |
| T 胜率 | 63.3% | **63.3%**（6:6，p=1.00） | **50.0%**（8:4，p=0.39） |
| 下包/局 | 10.77 | 10.37 | 10.13 |
| 拆包/局 | 7.47 | 6.40 | 6.77 |
| 伤害/回合 | 833 | 832 | 804 |
| 首杀转化 | 69.8% | 70.7% | 71.6% |
| 路径效率 | 0.49 | 0.48 | 0.48 |
| 方向反转 | 5802 | 6696 | 5514 |

分地图（B 新配置）：dust_2 50%→40%，mirage 70%→60%，ancient 70%→50%。

## 延迟（单局串行，真实玩家视角）

| 配置 | 均值 | p50 | p90 | p99 | max | >2.5s 占比 |
| --- | --- | --- | --- | --- | --- | --- |
| A 旧配置（260 tok / 手册 8KB / 全事件） | 2.95s | 2.98s | 4.35s | 5.22s | 6.05s | 56% |
| B 新配置（120 tok / 手册 4KB / 高价值事件） | **2.14s** | 1.95s | **3.52s** | 3.95s | 4.49s | **34%** |
| （历史）2 局并行 + 3B | 7.12s | 7.26s | 9.26s | — | 11.47s | — |

**校准的结论**：此前"T 胜率 −13.3pp"主要是并行拥塞（延迟 7s+）造成的，单局串行下旧配置与规则**完全相同**。

## 计划质量（B 新配置）

- 计划条数：规则 1811 / LLM 采纳 1212 / 顾问（只记录不执行）**140**
- 迟到丢弃：1（时效闸：决策期间减员且延迟 >2.5s）
- 意图：`default` 69%、retake 23%、rush 7%、stack 1%
- 整形改写率：24%（旧配置 31%）
- 计划分歧率：20%（同回合同队，规则与 LLM 首个计划不同）
- 顾问模式触发率：140 / 1352 ≈ **10%**（其余 90% 都被判定"有情报/经济优势"而放行）

## 结论

1. **单局串行下，旧配置与规则打平**（19 vs 19 胜，McNemar p=1.00）。
2. **新配置没有变好**：点估计 15 vs 19（p=0.39，不显著），延迟却确实从 2.95s 降到 2.14s。
3. 降低延迟解决了"计划过期"，但**没有转化为胜率**——说明瓶颈不在延迟，而在"LLM 给出的计划本身没有比规则更好"。
4. 按计划第 5 步：**默认关闭实时 LLM 教练**，`--coach=llm` 保留给分析与实验。

## 下一步（如果还想继续）

- 把 140 条"顾问计划"逐条对照规则计划与实际结果，找出"LLM 判断对但没执行"的样本；
- 或者承认实时教练这条路走不通，转成"赛后复盘 / 训练数据分析"工具（LLM 读比赛数据，输出改进建议，不参与实时决策）。

## 决策级证据（2026-11-06 补充）

用户质疑"只有数值、看不到每次决策"。为此新增**决策对比日志**（`*.decisions.csv`）：
同一决策点并排记录 **规则计划 / LLM 计划（含理由）/ 延迟 / 处置状态 / 最终执行 / 该回合结果**。

复现：

```powershell
# 15 局（3 图 × seed 1-5），默认配置
.\build-dev\dev_replay_runner.exe --coach=llm --coach-no-launch --jobs=1 --ticks=150000 `
    --maps=dust_2,mirage,ancient_ruins --seeds=1-5 --out=build-evidence/decision-final --tag=decision

# 生成可读对照文档（每条决策一行 + 理由行）
python tools/dev_replay/decision_review.py --dir=build-evidence/decision-final `
    --out=build-evidence/decision-review.md --max-games=6
```

### 统计（653 条决策 / 15 局）

| 状态 | 条数 |
| --- | --- |
| applied（采纳） | 572（其中 **370 条与规则不同**，占 65%） |
| advisory（只记录不执行） | 67 |
| invalid（硬规则拒绝） | 5 |
| empty（无回包） | 2 |

### 决策级胜率（按回合、每队取首个决策）

| 分组 | 回合数 | 该队胜 | 胜率 |
| --- | --- | --- | --- |
| 采纳且与规则不同 | 194 | 94 | **48.5%** |
| 采纳但与规则相同 | 120 | 63 | 52.5% |
| 顾问（不同意但未执行） | 47 | 24 | 51.1% |

**读法**：LLM 确实在 65% 的采纳里改变了打法，但这些回合的胜率没有更高（48.5% vs 52.5%，样本 194/120）。

### 这仍不是"证明 LLM 更差"

- 决策级胜率是**相关性**，不是反事实：同一局面下"如果执行规则计划会怎样"没有跑过。
- 要得到硬证据，需要**状态快照 + 双计划回放**（克隆 game，分别执行两套计划，比较结果）。
  当前 `CS2DGame` 没有快照/恢复能力，这是下一步要做的工程。
- 人类可读的对照文档已经生成：`build-evidence/decision-review.md`，可直接逐条判断。

# V2：可执行战术库 + 计划落地（2026-11-06）

## 这轮改了什么

| 项 | 内容 |
| --- | --- |
| 战术库 | 重写为 **42 张可执行战术卡**（每图 14 张：T 进攻 6 / 下包后 2 / CT 防守 3 / 回防 2 / 其他），`lint_playbook.py` 校验 **0 错误** |
| 注入体积 | `_common` 4.9KB + 地图 8KB ≈ **11.3KB/图**（此前默认上限 4000B，地图部分 **0%** 进入） |
| 新字段 | `SlotOrder` 增加 `lookArea/lookAngle/hold/util+utilArea`；BOT 消费朝向/站姿/投掷 |
| 战术表 | `gen_map_anchors.py` 从 TMJ 几何自动生成**每阵营驻守锚点**（29–35 个区域 × 2 阵营）与朝向；仅在卡片显式声明 `hold` 时启用 |
| digest | 新增 **敌枪构成**、**道具明细（烟/闪/火/雷）**、**近局习惯（主攻侧/首触/胜负）** |
| 自洽校验 | `target` 与槽位不匹配 → 用模板/规则回退；只改 target 的计划判为 **no-op**；下包后槽位走模板 |
| 卡片落地 | `materialize_cards.py` 把卡片写成 `[slots.<Team>.<Intent>@<Target>]`，规则教练与 LLM 共用同一套可执行模板 |

## 30 局配对（7B，单局串行，完整战术库）

| 指标 | 规则 | LLM | Δ |
| --- | --- | --- | --- |
| T 胜率 | 63.3% | 46.7% | −16.7pp（McNemar 8:3，**p=0.227 不显著**） |
| 下包/局 | 10.77 | 10.70 | −0.07 |
| 拆包/局 | 7.47 | 7.43 | −0.03 |
| 伤害/回合 | 833 | 810 | −23 |
| 首杀转化 | 69.8% | 68.4% | −1.4pp |
| 延迟 | — | 均值 3.20s / p90 4.39s | — |

LLM 意图分布明显被战术库改变：`default` 41%（旧 64%）、`stack_*` 29%、`retake_*` 22%。
但**胜率没有提升**；同期有 185 条计划因 `target↔槽位` 不自洽被拒。

## 12 局验证（模板落地补丁后）

| 指标 | 规则 | LLM | Δ |
| --- | --- | --- | --- |
| T 胜率 | 58.3% | 58.3% | **0.0** |
| 伤害/回合 | 820 | 825.6 | **+5.6** |
| 拆包/局 | 7.25 | 6.25 | −1.00 |
| 首杀转化 | 66.1% | 71.2% | **+5.1pp** |

拒绝情况：`invalid_consistency` 70、`invalid`（硬规则）55、advisory 57、applied 346。
说明"计划落地"仍有约 13% 被自洽校验拦下、10% 被硬规则拦下。

## 结论

1. **战术库确实改变了 LLM 的选择**（default 64%→41%，stack/retake 显著增加），且这些计划现在有槽位模板可执行。
2. **但胜率仍无提升**（30 局 −16.7pp，p=0.23；12 局 0.0）。伤害/首杀转化在 12 局里略有改善，需要更大样本确认。
3. 下一步最该做的不是继续扩战术库，而是**降低计划被拒率**（自洽 13% + 硬规则 10%），并检查
   `stack/retake` 这类"模板化计划"是否真的比规则层执行得更好。

# V3/V4：修「计划被拒」之后（2026-11-06）

## 修了什么

| 问题 | 修复 |
| --- | --- |
| `invalid_consistency` 185 条（下包后 `default→包点` 与槽位不匹配） | **语义规范化**：下包后 `default→A/B` 自动转成 `stack_A/B`（T）或 `retake_A/B`（CT），再套模板 |
| 下包后 `target` 为空 → 硬规则拒绝 | 用包点区域反推 `target`（`AreaSideOf`） |
| 诊断工具 | `analyze_postplant.py`：下包回合胜率、LLM 状态、计划 vs 结果 |

效果：`invalid_consistency` 从 185 → **5 条**；下包后 LLM 计划现在全部是 `stack_*` / `retake_*` 并套用模板。

## V3（24 局，语义规范化后）

| 指标 | 规则 | LLM | Δ |
| --- | --- | --- | --- |
| T 胜率 | 66.7% | 62.5% | −4.2pp |
| 拆包/局 | 7.25 | 8.17 | **+0.92** |
| 伤害/回合 | 828.5 | 798.4 | −30 |
| 首杀转化 | 69.9% | 67.6% | −2.3pp |

下包后专项：规则 64% T 胜 vs LLM 59%；LLM 下包后决策 `applied_diff` 136 回合，该队胜 53%。

## V4（18 局，补 target 反推后）

| 指标 | 规则 | LLM | Δ |
| --- | --- | --- | --- |
| T 胜率 | 61.1% | 44.4% | −16.7pp |
| 下包/局 | 9.94 | 10.56 | +0.61 |
| 拆包/局 | 6.89 | 7.61 | +0.72 |
| 伤害/回合 | 821.8 | 808.9 | −12.8 |
| 首杀转化 | 70.0% | 60.2% | **−9.9pp** |

状态：applied 614 / advisory 126 / **invalid 102（12%）** / consistency 5。

## 关键结论（修正）

1. 「计划被拒」问题基本修掉了（一致性拒绝 185→5），**但胜率没有因此改善**。
2. **下包后的卡片模板不如规则模板**：V3 下包回合 LLM 59% vs 规则 64%；V4 56% vs 66%。
   说明"卡片里把 5 人分散到外围"在模拟里确实劣于规则层"贴包 + 中路一人"的交叉站位。
3. 仍剩 12% 的 `invalid`（硬规则 plant/save 拒绝），以及首杀转化下降 9.9pp——
   这两项说明 LLM 在**开局那一枪**上的计划不如规则稳。

## 建议（下一步）

1. 下包后**直接交给规则模板**，LLM 只做赛前/回合开始决策（可配 `PE_COACH_PLANT_RULE=1`）。
2. 查 12% 的 `invalid`：抓 `[Coach] LLM 计划非法` 的原始回包分类，再决定是改写还是收窄 allow-set。
3. 若做了 1 仍无提升，结论维持：LLM 不适合实时教练，转赛后分析。
