# LLM 教练 A/B 实测结果

模型：`qwen2.5-7b-instruct-q4_k_m`，llama-server `-c 16384 --parallel 2`。
对局：3 张图 × seed 1–10 = **30 局配对**，`ticks=150000`（约 13 回合/局）。
规则组与 LLM 组使用完全相同的 map/seed/ticks，仅教练来源不同。

命令：

```powershell
# 规则组（毫秒级/局）
.\build-dev\dev_replay_runner.exe --coach=rule --ticks=150000 `
    --maps=dust_2,mirage,ancient_ruins --seeds=1-10 `
    --out=build-evidence/final-rule --tag=final-rule

# LLM 组（7B，全事件，2 局并行）
.\build-dev\dev_replay_runner.exe --coach=llm --llm-parallel=2 --jobs=2 `
    --ticks=150000 --maps=dust_2,mirage,ancient_ruins --seeds=1-10 `
    --out=build-evidence/final-llm --tag=final-llm

python tools/dev_replay/eval_llm.py --rule=build-evidence/final-rule --llm=build-evidence/final-llm
```

## LLM 计划质量

- 计划条数：规则 1807 / LLM 1356（去重后）
- 意图分布：`default` 64%、`retake_b` 10%、`retake_a` 8%、`stack_a` 6%、
  `rush_a` 4%、`rush_b` 4%、`stack_b` 4%
- 整形改写率：**31%**（约三分之一被 `SanitizeCoachPlan` 改写成默认分兵）
- 延迟：均值 **7.12s**、p50 7.26s、p90 9.26s、max 11.47s
  （这是 2 局并行、4 路请求争 2 个槽位的"加压"数据；单局实测是 1–5s）
- **计划分歧率 17%**：同一回合同一队，LLM 的首个计划与规则不同的比例

## 怎么解读（重要）

1. **没有证据表明当前 LLM 教练更好**。T 胜率点估计 −13pp，但 30 局的 95% 置信区间
   跨过 0（46~78% vs 33~67%），只能证明"没有显著提升"。
2. **dust_2 的 50%→20% 只有 10 局**，属于典型的小样本噪声区间，不要单独引用。
3. **延迟是硬伤**：p90 9.3s 意味着计划落地时局面已经变了；真实单人局 1–5s 会好一些，
   但仍是"教练看着 5 秒前的战场下命令"。
4. **64% 仍是 default**：模型大部分时候给的是保守方案，只有 17% 的回合真正改变了打法。
5. **31% 被整形掉**：这部分是"模型想打，规则层不让"，也是后续可调空间。

## 结论与下一步

- 结论：**框架可用**；当前"7B + 现有提示词 + 现有整形规则"没有展现出优于规则教练的证据。
- 下一步优先级：
  1. 降低延迟（单局串行、`max_tokens` 260→120、战术库 8KB→4KB）；
  2. 把"整形拦截"的 31% 拆开看：哪些是真该拦（无情报赌点），哪些是过度保守；
  3. 只在 LLM 有明确信息优势时接管（例如拿到具体站位情报），其余交给规则——
     "混合教练"比"全权交给 LLM"更可能赢。
