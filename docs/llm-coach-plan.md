# LLM 教练改造计划（待执行）

> 来源：2026-11-06 的 30 局 A/B 实测（见 `tools/dev_replay/LLM_EVAL_RESULTS.md`）。
> 结论：当前 LLM 教练**没有**优于规则教练，且问题定位在三处——延迟、保守、被规则层拦截。
> 本文件是后续改造的执行清单；完成一项勾掉一项，并更新实测数据。

## 执行顺序

### 第 1 步：测量校准（不改玩法）

- [ ] 用 `--jobs=1` 单局串行重跑 30 局配对，确认负结论里有多少是"并行拥塞"造成的假象
- [ ] 记录真实的单局延迟分布（p50/p90/p99），写回 `LLM_EVAL_RESULTS.md`
- **验收**：同一批 seed 的 T 胜率与延迟都有一份"无并行干扰"的数字

### 第 2 步：计划时效性指标（真正的 KPI）

- [ ] 计划 trace 增加"是否在下一个关键事件（首触/下包/拆包）之前落地"
- [ ] `eval_llm.py` 输出**迟到率**：`迟到计划 / 总计划`
- [ ] 定义硬闸：回包晚于 2.5s 且期间有关键事件 → 丢弃并计为迟到
- **验收**：能看到"多少 LLM 计划其实是在对昨天的战场下命令"

### 第 3 步：顾问模式（混合教练）

- [ ] 规则教练始终掌握节奏；LLM 只在**有信息优势**时覆盖：
  - 拿到具体站位情报（某侧 N 人）
  - 或经济差达到阈值
- [ ] 无信息优势时，LLM 计划只记录不执行（用于对比分析）
- [ ] 保留 `source` 标记，区分 `rule` / `llm` / `llm_advisory`
- **验收**：同样的 30 局配对里，T 胜率不低于规则组，且迟到率显著下降

### 第 4 步：延迟优化（辅助）

- [ ] `max_tokens` 260 → 120（`reason` 限制 20 字内）
- [ ] 战术库 8KB → 4KB（`_common` + 地图手册压缩）
- [ ] 只在高价值事件请求 LLM（回合开始 + 下包后），mid-round 事件不再请求
- **验收**：单局 p90 ≤ 3s

### 第 5 步：复盘

- [ ] 30 局配对 A/B（7B、全事件、单局串行）
- [ ] 若仍无提升，把 LLM 降级为"训练/分析工具"，不再作为实时教练

## 约束

- 每一步都必须用同一批 `map/seed/ticks` 配对比较，禁止跨批次比较
- 3B 模型只用于吞吐筛选，结论性数字必须 7B
- 任何玩法改动都要过 `gameplay_tests`（当前 188 通过）与确定性双跑
