# LLM 教练改造计划（待执行）

> 来源：2026-11-06 的 30 局 A/B 实测（见 `tools/dev_replay/LLM_EVAL_RESULTS.md`）。
> 结论：当前 LLM 教练**没有**优于规则教练，且问题定位在三处——延迟、保守、被规则层拦截。
> 本文件是后续改造的执行清单；完成一项勾掉一项，并更新实测数据。

## 执行顺序

### 第 1 步：测量校准（不改玩法）

- [x] 用 `--jobs=1` 单局串行重跑 30 局配对（旧配置），产物 `build-evidence/step1-calib`
- [ ] 记录真实的单局延迟分布（p50/p90/p99），写回 `LLM_EVAL_RESULTS.md`
- **验收**：同一批 seed 的 T 胜率与延迟都有一份"无并行干扰"的数字

### 第 2 步：计划时效性指标（真正的 KPI）

- [x] 时效硬闸：回包时存活数变化 且 延迟 > 2.5s → 丢弃并计数（`PE_COACH_STALE` / `PE_COACH_STALE_MS`）
- [x] `llm_plans` / `llm_advisory` / `llm_late` 进 `summary.csv`，`eval_llm.py` 输出迟到率
- [x] 硬闸已实现（同上）
- **验收**：能看到"多少 LLM 计划其实是在对昨天的战场下命令"

### 第 3 步：顾问模式（混合教练）

- [x] 规则教练始终掌握节奏；LLM 只在**有信息优势**时覆盖（`PE_COACH_HYBRID`，默认开）：
  - 拿到具体站位情报（某侧 N 人）
  - 或经济差达到阈值
- [x] 无信息优势时只记录不执行（`source=llm_advisory`，写进 plans.csv）
- [x] `source` 区分 `rule` / `llm` / `llm_advisory`
- **验收**：同样的 30 局配对里，T 胜率不低于规则组，且迟到率显著下降

### 第 4 步：延迟优化（辅助）

- [x] `max_tokens` 260 → 120（`PE_COACH_MAXTOK`）；`reason` 截断 20 字符（`PE_COACH_REASON_CHARS`）
- [x] 战术库 8KB → 4KB（`PE_COACH_PLAYBOOK`）
- [x] 只在高价值事件请求 LLM（回合开始 + 下包后；`PE_COACH_EVENTS=all` 恢复旧行为）
- **验收**：单局 p90 ≤ 3s

### 第 5 步：复盘

- [x] 30 局配对 A/B（7B、单局串行）→ `build-evidence/step1-calib`（旧配置）与 `build-evidence/step5-final`（新配置）
- [x] 仍无提升 → 默认关闭实时 LLM 教练（`main.cpp: coachLlm = false`），`--coach=llm` 保留给分析/实验

## 约束

- 每一步都必须用同一批 `map/seed/ticks` 配对比较，禁止跨批次比较
- 3B 模型只用于吞吐筛选，结论性数字必须 7B
- 任何玩法改动都要过 `gameplay_tests`（当前 188 通过）与确定性双跑
